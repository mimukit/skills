# Plan: dbkit

Grilled: 2026-11-09

## Context

Agents make the same database mistakes in every project. They add a `NOT NULL` column with no default to a large table, build an index without `CONCURRENTLY`, rename a column in one deploy while old code still reads it, mix a backfill into the schema migration, forget that Postgres does not index a foreign key column, pick `timestamp` over `timestamptz`, and "fix" a slow query by adding an index without a plan before or after. None of this fails a test on a seed database of 40 rows. It fails in production, under lock, at the size the dev database never reaches.

The collection has no skill for this work. Two skills touch the data layer at its edges, and dbkit must leave both alone: `qakit` reads [db.md](../../skills/qakit/db.md) to write read-only database checks into a QA plan, and `gitkit prepare` makes a worktree's own dev database. `plankit` asks for a `Migration and rollback` section but gives no rules for one. `reviewkit`'s Pass 4 checks data bounds for the UI, not migration safety.

dbkit is one public skill with four modes. `design` models tables and schema changes. `migrate` writes or checks a migration so it is safe on a live database. `tune` finds why a query is slow, from a production plan. `audit` sweeps a whole schema and its migration history for the breaks the other three modes prevent.

Success: each mode fires on its own trigger phrases and does not take `debugkit`'s or `qakit`'s; one manual run per mode on a real Drizzle and Postgres repo produces the result the mode promises; dbkit never connects to a host it was not cleared for.

Target: every case in `skills/dbkit/evals/triggers.md` returns its expected result, and the owner's manual runs in the last phase pass on `~/projects/primeshopr` and `~/projects/growaloy`. Size target (proposed; baseline about 15,000 words across the five sources): the root stays at or under 3,000 words and the whole skill at or under 9,000.

The sources state the same rules in several places: concurrent index creation appears in three of them. dbkit states each rule once, in the root or in one engine satellite, and every mode applies it.

Every source has the same gap: no lock budget. None sets `lock_timeout` before DDL, none says which statement takes which lock, and none says how to recover an `INVALID` index left by a failed concurrent build. dbkit adds these, because they are the difference between a slow migration and an outage.

## Design decisions (settled)

| Decision | Resolution |
|----------|-----------|
| Name | `dbkit`, settled 2026-11-09. "db" is the word people search, it covers SQL and document stores, and it follows the shorten rule (`databasekit` is the clumsy join). Collision check on 2026-11-09: the largest GitHub repo named `dbkit` has 74 stars, and the npm `dbkit` package is a small library, so neither is the well-known tool the collision rule names. |
| Visibility | Public, `metadata.internal: false`. Portable: conventions inlined, no repo-relative links, degrades to a printed report with no filesystem. |
| Modes | `design`, `migrate`, `tune`, `audit`, settled 2026-11-09. Each is a distinct moment a person chooses, and each has its own trigger vocabulary. |
| One skill or four | One skill. The four modes share the schema standard, the engine satellites, and the connection guard, so four skills would state them four times. |
| Layout | Routing root plus `modes/<mode>.md`, the fixed mode-satellite shape. Engine rules live in `engines/<engine>.md` and ORM gotchas in `orms.md`, each read only on its branch. `evals/triggers.md` holds the trigger cases, as in motionkit. |
| The schema standard | One engine-neutral body in the root that `design`, `migrate`, and `audit` all apply: naming, keys, nullability, constraints, foreign key indexes, money and time types, normalize first and denormalize only on a measured read. Engine-specific facts (type names, lock levels, version limits) live in the engine satellite. This is motionkit's "motion standard" pattern. |
| Project conventions win | dbkit reads the existing schema before it writes. When the repo uses `camelCase` columns, singular table names, or `uuid` keys throughout, dbkit follows them and reports a break from its own standard as a finding, never as a silent rewrite. The precedence matches AGENTS.md: user instruction, then repo convention, then the standard. |
| Engines | Postgres deep, MySQL and SQLite light, settled 2026-11-09. `engines/postgres.md` carries the lock table per DDL statement, `lock_timeout` and `statement_timeout`, `CONCURRENTLY` outside a transaction and `INVALID` index recovery, version limits (PG 11 instant defaults, PG 15 `NULLS NOT DISTINCT`, PG 18 `uuidv7()`), and partition rules. `mysql.md` and `sqlite.md` carry a short gotcha list each: MySQL online DDL `ALGORITHM=INSTANT` and `INPLACE`, InnoDB clustered primary key, `utf8mb4`; SQLite `ALTER` limits and the table-rebuild recipe, `PRAGMA foreign_keys`, `STRICT` tables, WAL. Any other engine gets the engine-neutral standard and a plain statement of what dbkit does not cover. |
| Document stores | Not covered, kept from the draft. MongoDB and DynamoDB repos get the plain "not covered" statement. |
| ORM layer | Detected, not taught. dbkit finds the tool (Drizzle, Prisma, Kysely, Django, Rails, golang-migrate, raw SQL) from the repo and uses its own generator, read from `--help`. `orms.md` holds only the gotchas no config confesses: which tool wraps each migration in a transaction (and so breaks `CONCURRENTLY`), which command is dev-only (`drizzle-kit push`, `prisma migrate reset`), and how to drop to raw SQL in each. |
| Generators that need a database | A generator that connects to a database (`prisma migrate dev`, a shadow database) runs only against a disposable target, with `--create-only` where the tool has it. Otherwise dbkit writes the SQL by hand and says so (grill Q8, defaulted). |
| Connection guard | Read-only and local only, settled 2026-11-09. Before the first connection, dbkit resolves the host, states it, and connects only to `localhost`, a container service from the compose file, or a host the user confirms in this session. It runs `SELECT`, `EXPLAIN`, and catalog queries only. `EXPLAIN ANALYZE` executes the query, so it runs only on a disposable target, and never on a statement that writes. dbkit never runs a script whose name marks production (`db:prod:*`, `*:production`, an `env-deploy` wrapper). The guard has no write exception (grill Q10). This states qakit `db.md`'s rule as a conclusion, which the portability seam allows. |
| Disposable target | The same definition as qakit, stated inline: a target the project's agent instruction file names as throwaway, or a gitkit `prepare` worktree database (grill Q14, defaulted). |
| Writes to the repo | `design` and `migrate` edit the schema source and write migration files through the project's generator. `tune` and `audit` change no code and write a report. No mode applies a migration to any database; the user or the project's own command does that. |
| `design` output | The schema edit in the project's own schema source, the generated migration, and a decisions table in chat (each table, key, constraint, and index with a one-line reason). It then runs `migrate`'s check on the generated file before it reports. A Mermaid ER diagram only when the change adds three or more related tables. |
| `migrate` output | Two branches. **Write**: a migration for a stated change, with the deploy order and a rollback line per step. **Check**: a risk table for an existing migration or a diff, one row per statement: the statement, the lock it takes, the table it locks, and a verdict (safe, safe with a change, unsafe). Its rollback section uses plankit's `Migration and rollback` shape, so it pastes into a plan. |
| `migrate` verdict basis | The lock class decides first. A statement that takes `ACCESS EXCLUSIVE` or rewrites the table needs a `lock_timeout` at any table size, because a lock queued behind a long query blocks every write. Only scan or rewrite time takes a size condition, stated as "unsafe above N rows", so the verdict holds without a production row count (grill Q6, defaulted). |
| Expand-contract files | `migrate` writes only the files safe for the current deploy. The contract step goes in the hand-off with its trigger condition ("after deploy N is live and no code reads `old_col`"), and into the plan's `Migration and rollback` section when a plan exists. The rule: never write a migration that must wait for a later deploy into the migrations directory (grill Q3). With no plan file, the hand-off suggests filing the step with **issuekit** when it is installed, and otherwise a TODO (grill Q13, defaulted). |
| `tune` evidence | A production plan is the main evidence: the user pastes `EXPLAIN (ANALYZE, BUFFERS)` from where the query is slow. A local plan counts only when its row counts are within 10× of the production counts the user states; otherwise it shows plan shape only. Every claim is labeled "from plan" or "from code". With no pasted plan, `tune` gives the exact `EXPLAIN` command to run and stops (grill Q2). N+1 patterns are read from code (a query inside a loop, an ORM relation loaded per row). |
| `tune` index trials | Propose only (grill Q10). `tune` writes the candidate index and, when the target has the `hypopg` extension, a hypothetical-index check for the user to run where the slow plan came from. dbkit runs nothing. The "plan after" in the report comes from the user's run. |
| `tune` to `migrate` | A proposed index ships through `migrate` write, with `CONCURRENTLY` and `lock_timeout`, so every DDL takes one path (grill Q12, defaulted). |
| `tune` output | A report in chat: the query, the baseline plan, the diagnosis from the symptom table, one proposed change, and the user-run check. |
| `audit` output | A report at `docs/reviews/NNNN-review-schema-<slug>-YYYY-MM-DD.md` (grill Q7, defaulted), each finding with a `file:line` quote and a severity, ranked, one fix crowned and routed. Findings that need production statistics (unused indexes, bloat, table sizes) are listed as "needs production stats" with the catalog query to run, never guessed from the dev database. Migration history hygiene is part of the sweep: an applied migration edited after it merged (from `git log`), DDL and DML in one file, a dev-only command in a deploy script. |
| Boundary with debugkit | debugkit owns a symptom with an unknown cause, "this page got slow" included. dbkit `tune` fires only on query words: "this query is slow", "explain this plan", "add an index for this query". debugkit's hand-off gains one route: cause is a query → dbkit `tune` (grill Q1). |
| Boundary with qakit | "Check this migration" goes to dbkit `migrate`. qakit keeps the behavior tests after the change (grill Q5, defaulted). |
| Sibling routes | reviewkit's Pass 4 names dbkit `migrate` check when the diff adds a migration file. plankit's hand-off offers dbkit `design` when the plan has a `Migration and rollback` section. Both name dbkit only when it is installed and give a plain fallback. afkkit gets no route in this plan (grill Q4). |
| Collection group | `Building` in `skills.sh.json`, with the group description extended to name the data layer. `design` and `migrate` are build work; `tune` and `audit` route their fix to a build. |
| Test approach | No new runner. `make lint` and the trigger cases in `evals/triggers.md` gate the build phases. The owner runs the fixture checks by hand in the last phase; the build does not touch `~/projects/primeshopr` or `~/projects/growaloy` (grill Q11). |
| Commits | The build leaves every change uncommitted for the owner's review (grill Q15, defaulted). |

## Approach

The root holds mode selection, the connection guard, the disposable-target definition, engine and ORM detection, the project-conventions rule, and the schema standard. Each mode file assumes the root is loaded. Each engine file is read once the engine is known; a mode never reads an engine file it does not need.

It reuses:

- **motionkit's shape**: a standard in the root that every mode applies, mode satellites, `evals/triggers.md`, and a source analysis with credit lines.
- **qakit `db.md`'s guard and `DB_CMD`**: one client invocation discovered from the repo, and the host check before the first connection. dbkit states the answer and does not import the file.
- **plankit's `Migration and rollback` section**: `migrate` writes its rollback and its deferred contract step in that shape.
- **gitkit `prepare`**: a worktree's dev database is how dbkit gets a disposable target. dbkit reads the project's declaration and never makes a database itself.
- **The artifact naming rule**: the `audit` report takes the next serial in `docs/reviews/`, scanned across worktrees and `origin/<base>`, stated inline because the skill is public.

Rejected: a static-only skill (the user chose read-only access, and `tune` without a plan is guesswork), four separate skills (three shared bodies stated four times), and seeded volume on a local database for `tune` (it breaks the guard, and synthetic data misleads the planner).

Phases 1 to 5 can run unattended. Phase 6 is attended and comes last because it verifies the build; an unattended runner stops before it.

## Open questions

None. Every grill question is settled.

## Non-goals

- Cloud cost, instance sizing, reserved capacity, and storage tiers.
- Replication, failover, backups, and disaster recovery.
- Server configuration (`shared_buffers`, `work_mem`, `innodb_buffer_pool_size`) beyond naming it as a cause in `tune`.
- Migration observability dashboards and change data capture.
- Applying a migration to any database, running any production script, or creating any index, real or trial.
- Runtime QA of a feature's data writes, which qakit `db.md` owns.
- Making a worktree's dev database, which gitkit `prepare` owns.
- Deep MySQL or SQLite tuning, and any document-store modeling.
- An afkkit route to dbkit.
