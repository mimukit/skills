# Plan — prototypekit

_Created 2026-08-07._

## Context

Every skill in this collection assumes the question is already settled. `validatekit` asks whether an idea is worth building and stops at a verdict. `researchkit` reads primary sources and recommends an option — and is emphatic that it **never builds to find out**, because a surprise prototype buries the comparison the user asked for. `plankit` drafts, `grillkit` interrogates, `issuekit` files, `implementkit` builds production code behind a done-gate. At no point does anything in the loop write code whose purpose is to *answer* rather than to *ship*.

So when a decision genuinely can't be settled by reading — does this state model hold up once you push refunds through it, what should this screen actually look like — the loop has no move. researchkit names the gap explicitly and then misroutes it: *"Building one is a separate, explicitly requested job, and implementkit's, not researchkit's."* It isn't implementkit's. implementkit requires a settled intent, writes production code, and gates on the repo's tests — every one of which is wrong for a throwaway. The user is left to either hand-roll the spike or, worse, let an agent quietly build a prototype-shaped thing inside the real codebase where it never gets deleted.

**prototypekit is that move.** Throwaway code that answers a question, where the question decides the shape. It sits in the DECIDE phase alongside `validatekit` and `researchkit`, takes the cases those two refuse, and hands its answer forward into planning. The code is disposable by construction; the answer is the deliverable.

**Success:** ask "does this reducer survive partial refunds" and get a single HTML file you can click through the hard cases in, then a verdict and nothing left on disk. Ask "what should this settings page look like" and get three genuinely different mocks on one route, switchable, then the choice folded into a plan and the mocks gone.

This plan is *my version of* [`mattpocock/skills` → `engineering/prototype`](https://github.com/mattpocock/skills/blob/main/skills/engineering/prototype/SKILL.md) — authored from scratch to this collection's conventions, keeping its two-branch split and its thesis, and replacing its capture story with one that fits a loop already built out of gitignored scratch.

## Design decisions (settled)

Settled with the user on 2026-08-07 in the plankit scoping pass. Four of these were chosen against my recommendation, and the plan is better for it — the lean readings hold, and the one real cost is named under Open questions rather than papered over.

| Decision | Resolution |
|----------|-----------|
| **Name** | `prototypekit` — per the backlog row. "Prototype" leads so search works, it collides with nothing well-known, and it's the word a user actually types. Rejected `spikekit` (shorter and it *is* the term of art, but "spike" is jargon a non-agile reader misses, and it names only the narrowest of the two branches), `mockkit` (names only the other branch). |
| **Modes** | **Two: `logic` / `ui`**, exactly as the reference splits them. The split is justified by artifact shape, not topic — `logic` produces one interactive HTML file a human drives through states, `ui` produces N variants on one route you switch between. Those are different enough that getting the branch wrong wastes the whole prototype. Rejected a third `spike` mode for feasibility probes: it would have given researchkit's misroute a precise home, but it doubles the surface for a case that `logic` can absorb by widening its framing from "does this state model feel right" to "does this behavior hold up". The absorption is the weak seam and it is an [open question](#open-questions), not a settled one. |
| **The question gate** | **No question, no prototype.** Before writing a line, prototypekit states the question and the decision it unblocks, in one sentence each. An ask that resolves to "build me a demo", "make a proof of concept for the client", or "just try something" is **bounced** — that's production work under a softer name, and it belongs to plankit → implementkit. This is prototypekit's version of implementkit's bounce-if-thin, and it's the same success-not-failure framing: refusing to build a prototype with no question attached is the boundary that keeps the skill honest. |
| **The stop condition** | **Stop when the question is answered, not when the prototype feels finished.** Named as a first-class rule because the failure mode is specific and gradual: a spike that works invites one more case, then error handling, then a component extraction, and the throwaway quietly becomes an app nobody chose to build. The moment the answer is legible, prototypekit stops adding and moves to the verdict. |
| **Where the code lives** | **In the main working tree, next to what it prototypes, gitignored.** The reference's rule — locate it close to where it will actually be used, so the imports, aliases, config, and dev server all just work — wins over isolation. Rejected a `gitkit` worktree on a `prototype-<slug>` branch (cleanest disposal in the collection and it would have preserved the reference's primary-source capture, but it's real ceremony for a file you intend to delete within the hour) and an out-of-repo scratch dir (maximum safety, and it forfeits the project imports that make a prototype worth building against a real codebase at all). |
| **The naming convention is load-bearing** | Every prototype file is named `*.prototype.*` (or `*.prototype/` for a directory), and **that pattern is what the gitignore entry matches**. This is not cosmetic. It's the single mechanism standing between a throwaway and a commit, so the skill states it as a rule with a consequence attached rather than a style note — a prototype file that doesn't carry the marker isn't ignored, and an unignored prototype is one `git add -A` from main. It doubles as the reference's "clearly marked as such": a casual reader sees `cart.prototype.html` and knows. |
| **The gitignore edit** | **Add the pattern before writing the first file, and say so in the same line** — `designkit`'s swatch-sheet precedent verbatim ("write it to a gitignored scratch path, add that path to `.gitignore` if it isn't covered, name it in the consent ask, and don't keep it"), which `statuskit` follows for `docs/status/` too. Skip the edit when the path is already covered or the repo has no `.gitignore` worth touching. A collection that already edits `.gitignore` in two skills for exactly this reason shouldn't invent a third policy here. |
| **What survives** | **No new artifact type.** The answer goes back into whatever asked the question — the plan's **Open questions**, an issue comment, or the chat when neither exists. Rejected `docs/prototypes/prototype-<slug>-YYYY-MM-DD.md` (a ninth `docs/` directory whose contents would be one paragraph). The verdict has a fixed four-line shape wherever it lands — **question · what was built · what it showed · the answer** — so the deliverable is uniform even without a file of its own. |
| **Capture, reconciled** | The reference's rule 6 keeps the prototype as a **primary source** on a throwaway branch. With no worktree and no new artifact, that mechanism is gone — so it returns as an **offer at hand-off, never a default**: "park this on `prototype-<slug>` before I delete it?" One `git checkout -b && git add -f && git commit`, then back. Off by default because the whole premise is that the answer matters and the code doesn't; available because occasionally the code *is* the argument. Whether the default is right is an [open question](#open-questions). |
| **Disposal is explicit, not implied** | prototypekit **deletes the prototype files itself at hand-off**, having offered the park first, and reports what it removed. A skill that leaves gitignored debris behind and calls it disposable is relying on the user to finish the job — and gitignored files are exactly the ones nobody notices for six months. Deleting a file the skill created in the same session is the safe class of delete; anything it didn't create, it doesn't touch. |
| **Boundary — researchkit** | researchkit's **Never build to find out** stance is **correct and stays**; only its destination is wrong. Three lines change from "that's implementkit's job" to "that's prototypekit's", and its Open questions template already says *"settling this needs a spike: `<what it would measure>`"* — which becomes a clean hand-off sentence instead of a dead end. The two skills are complements: researchkit answers from sources and never builds, prototypekit answers by building and never cites. |
| **Boundary — implementkit** | **A prototype is never promoted.** Folding a validated decision into the real code is a *fresh* implementkit run against the real files, with its own input, mode resolution, and done-gate — not a copy of the prototype with the marker filed off. Stated in both directions: prototypekit never hands implementkit a file to adopt, and implementkit's bounce-if-thin now has a second destination, since "the design isn't settled because nobody has seen it work" routes here rather than only to grillkit. |
| **Boundary — uikit** | **Borrow the floor, own the divergence.** When uikit is installed, `ui` mode takes its anti-slop catalog and accessibility floor — mocks you're choosing between shouldn't be choosing between three flavors of LLM default. It **overrides uikit's precedence ladder for this job only**, because that ladder's whole purpose is conformity to `DESIGN.md` and the shipped components, and three variants that all conform are variants of one idea, not a choice. That's precisely the failure plankit's own diverge step warns about, one layer down. Once a variant wins, **uikit builds it for real, from scratch, at full ladder** — the mock is evidence, not a starting point. |
| **Boundary — commitkit / reviewkit** | Both are protected by the gitignore, and neither needs to change. commitkit stages from the working tree and won't see an ignored file; reviewkit targets uncommitted work and won't either. This is the argument that makes in-tree placement survivable, and it's why the naming convention is load-bearing rather than decorative — the guard is the ignore, and the ignore is the name. |
| **Unattended runs** | **Out of `afkkit`'s span, and out of every unattended path.** A prototype exists to produce a judgment a human then makes; running one with nobody watching produces a deleted file and an answer nobody read. prototypekit is a DECIDE-phase kit like `validatekit` and `researchkit`, which sit outside the span for the same reason. It is interactive-only, in the same class as `mergekit`. |
| **The variant switcher** | The reference's mechanic — one route, a URL search param, a floating bottom bar — ships as the **pattern with its rationale** (a single route means one dev-server start and a shareable link per variant), not as React code. Follow whatever routing the project already uses, and never invent a new top-level structure to hold a mock. |
| **Visibility** | **Public** (`internal: false`). Conventions inlined, no repo-relative links, no dependency on `make`/`AGENTS.md`/`scripts/`. Degrades to printing the prototype as fenced blocks with their intended paths when there's no writable filesystem — at which point the disposal problem solves itself. |
| **Layout** | **Single flat `skills/prototypekit/SKILL.md`.** Two modes with a recipe each fit one file comfortably — `issuekit` runs five modes in 504 lines. The reference splits into `SKILL.md` + `LOGIC.md` + `UI.md` for progressive disclosure, which is a real benefit in a collection organized that way; here, all 24 skills are single-file and `verifykit`'s helper script is the only second file anywhere. Consistency wins at this size. |

## Approach

**Reuses, rather than reinvents:** `designkit`'s gitignored-scratch discipline for review scaffolding, including the say-it-in-the-same-line consent phrasing; `statuskit`'s `.gitignore`-edit precedent and its disposable-by-design framing; `implementkit`'s bounce-if-thin gate, restated for questions instead of specs; `researchkit`'s never-build-to-find-out prose as the mirror image that names this skill's own boundary; `uikit`'s anti-slop catalog and accessibility floor, borrowed under an explicit ladder override; `plankit`'s variants-vs-distinct test, applied to UI mocks; the `Hand off` three-beat closing and the `plan-<slug>-YYYY-MM-DD.md` convention already in force. The reference contributes the two-branch thesis, the six shared rules, and the switcher mechanic.

### Phase 1 — Frontmatter, triggers, and the boundary paragraph

Write `name` / `description` / `license` / `metadata.internal: false` with a front-loaded "Use when…" trigger covering both branches and the plain-English asks — "prototype this", "spike this", "throwaway explore X", "does this state model hold up", "show me a few options for this screen", "mock up three versions". The opening names what prototypekit is **not**: not implementkit (production code, gated), not researchkit (answers from sources, never builds), not uikit (builds the UI that ships), and not a demo generator. Three of those are sibling skills; the fourth is the shape the request most often arrives disguised as.

### Phase 2 — The question gate and branch routing

The step before any code. State **the question** and **the decision it unblocks**, one sentence each, and bounce anything that resolves to "build me a demo" back to plankit → implementkit with the specific reason named. Then route: a state model, a reducer, a flow, a backend module → `logic`; a page, a screen, a component → `ui`. Where the ask is genuinely ambiguous and the user isn't reachable, default by what surrounds the code and **state the assumption at the top of the prototype** — the reference's rule, kept because a stated wrong assumption is correctable and a silent one isn't.

### Phase 3 — The shared rules

The six that apply to both branches, adapted to this collection's mechanisms rather than restated:

1. **Throwaway from day one, and marked.** Next to what it prototypes; `*.prototype.*`; the gitignore entry added first and named in the same line.
2. **Trivial to run.** One command from the project's own task runner, or a file you double-click. Discover the runner from the repo (`package.json`, `Makefile`, `justfile`, `pyproject.toml`) rather than assuming one.
3. **No persistence.** State lives in memory. Persistence is usually the thing being checked, not something to depend on; when the question genuinely involves a database, a scratch DB named `PROTOTYPE_wipe_me`.
4. **Skip the polish.** No tests, no abstractions, no error handling past what makes it run. prototypekit **never runs a done-gate** — there is nothing to gate.
5. **Surface the state.** Every action (logic) or variant switch (ui) renders the full relevant state. An invisible prototype answers nothing.
6. **Stop when it's answered.** The stop condition, restated where it fires.

### Phase 4 — Mode: `logic`

Build **one self-contained HTML file** — no build step, no server, double-click to open, and shareable as a single attachment to someone who doesn't have the repo. Two halves: **free-play controls** that fire every transition, and **tabbed guided walkthroughs** that push the model through the specific cases that are hard to reason about on paper — the ones the question is actually about. Full state rendered after every action. A non-developer must be able to drive it, because "does this feel right" is frequently a question only a non-developer can answer.

### Phase 5 — Mode: `ui`

**Several radically different variations on a single route**, switchable via a URL search param and a floating bottom bar, so one dev-server start covers all of them and each variant has a shareable link. Divergence is the deliverable: three variants of one idea is a failed prototype, and the section says so with the same test plankit applies to its own options. Borrow uikit's anti-slop catalog and accessibility floor when installed; override its precedence ladder here and say so out loud. Naming and routing follow whatever the project already does.

### Phase 6 — Disposal, capture, and the verdict

The closing sequence, in order: **verdict** (question · what was built · what it showed · the answer) written back into the plan's Open questions, the issue, or the chat → **offer the park** (`prototype-<slug>` branch, off by default) → **delete the prototype files** and report exactly what was removed. Then `## Hand off`, three beats: what changed (files created and now deleted, the gitignore entry, whether the branch park happened), where the answer landed, and one next move — normally `plankit`/`grillkit` to fold the answer into the plan, `uikit` when a variant won and needs building for real, and `domainkit` when the answer settled a hard-to-reverse trade-off worth an ADR. Each named only when installed, each with a plain-language fallback.

### Phase 7 — Integration

- **`researchkit`** — three lines redirected from implementkit to prototypekit (the **Never build to find out** close, the primary-sources spike aside, and the Open questions template note). Its stance is unchanged; only the destination moves.
- **`implementkit`** — one line in its bounce step: an input thin because *nobody has seen the design work* routes to prototypekit, alongside the existing grillkit/plankit routes.
- **`WORKFLOW.md`** — prototypekit added to the DECIDE phase next to `validatekit` and `researchkit`, in both the ASCII map and the Mermaid diagram, with a short section covering both modes and the never-unattended note.
- **`README.md`** skills table, **`skills.sh.json`** (the **Planning & Design** group), and the `prototypekit` row **deleted from `IDEAS.md`** per its own graduation rule.

### Phase 8 — Test live

`make link`, run both modes against a real project — a state model for `logic`, a real screen for `ui` — confirm the gitignore entry fires and nothing survives that shouldn't, then `make lint`.

## Open questions

1. **Does the two-mode split leave feasibility probes homeless?** The load-bearing one. "Is this library fast enough", "do these two things actually interop", "does this API do what its docs imply" is the exact case researchkit refuses and now routes here — and its artifact is a harness you run for a number, not a clickable state explorer. The plan absorbs it into `logic` by widening that branch's framing. Grill whether that widening holds or whether it quietly makes `logic` two modes wearing one name.
2. **Should the branch park be the default rather than an offer?** The reference argues the prototype *is* a primary source worth keeping, and the chosen shape demotes that to an opt-in nobody will take. Grill whether the answer alone is genuinely sufficient, or whether "what did we actually build" is the thing you want six weeks later when the decision gets relitigated.
3. **Is editing someone's `.gitignore` the right guard, and is `*.prototype.*` the right pattern?** Two skills already do it, so the precedent is set — but this is the only one where the edit is load-bearing rather than tidy. Grill the failure mode: a prototype file that misses the marker, a repo with a committed `.gitignore` under review, a monorepo with nested ignores.
4. **How does prototypekit know it has gone too far?** The stop condition is stated as a judgment ("stop when the question is answered") with no mechanism. A time box is meaningless to an agent. Grill whether a **scope box** declared upfront — the cases in, the cases explicitly out — is checkable enough to bite, or whether this stays a rule that only works when the model is already behaving.
5. **What happens when the prototype answers a *different* question than the one asked?** The most valuable outcome of a real spike, and the plan has no route for it. Grill whether prototypekit reports and stops, or is licensed to follow the new question.

## Non-goals

- **Not production code.** No tests, no error handling, no abstractions, no done-gate — and never promoted. Folding a validated decision into the real code is a fresh `implementkit` run.
- **Not a demo generator.** A prototype answers a question. Something built to show a client or a stakeholder is production work under a softer name, and it bounces.
- **Not the research step.** `researchkit` answers from primary sources and never builds. prototypekit answers by building and cites nothing.
- **Not the UI builder.** `uikit` builds the UI that ships. prototypekit's mocks exist to be compared, chosen between, and deleted.
- **Not a design-system artifact.** It reads `DESIGN.md` only through uikit's floor and never writes it — that's `designkit`'s, exclusively.
- **Never unattended.** Out of `afkkit`'s span and every autonomous path; the deliverable is a human judgment.
- **Does not commit** (except the explicitly offered branch park), does not push, does not open a PR, does not file an issue.
- **Not a scratch-file manager.** It disposes of what it created in this session and nothing else.
