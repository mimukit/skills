# Plan — prototypekit

Grilled: 2026-08-07

_Created 2026-08-07._

## Context

Every skill in this collection assumes the question is already settled. `validatekit` asks whether an idea is worth building and stops at a verdict. `researchkit` reads primary sources and recommends an option — and is emphatic that it **never builds to find out**, because a surprise prototype buries the comparison the user asked for. `plankit` drafts, `grillkit` interrogates, `issuekit` files, `implementkit` builds production code behind a done-gate. At no point does anything in the loop write code whose purpose is to *answer* rather than to *ship*.

So when a decision genuinely can't be settled by reading — does this state model hold up once you push refunds through it, what should this screen actually look like — the loop has no move. researchkit names the gap explicitly and then misroutes it: *"Building one is a separate, explicitly requested job, and implementkit's, not researchkit's."* It isn't implementkit's. implementkit requires a settled intent, writes production code, and gates on the repo's tests — every one of which is wrong for a throwaway. The user is left to either hand-roll the spike or, worse, let an agent quietly build a prototype-shaped thing inside the real codebase where it never gets deleted.

**prototypekit is that move.** Throwaway code that answers a question, where the question decides the shape. It sits in the DECIDE phase alongside `validatekit` and `researchkit`, takes the cases those two refuse, and hands its answer forward into planning. The code is disposable by construction; the answer is the deliverable.

**Success:** ask "does this reducer survive partial refunds" and get something you can drive the hard cases through, then a verdict and nothing left on disk. Ask "what should this settings page look like" and get three structurally different mocks on one route, switchable, then the choice folded into a plan and the mocks gone.

This plan is *my version of* [`mattpocock/skills` → `engineering/prototype`](https://github.com/mattpocock/skills/blob/main/skills/engineering/prototype/SKILL.md) — authored from scratch to this collection's conventions, keeping its two-branch split and its thesis, and replacing its capture story with one that fits a loop already built out of session-scoped scratch.

## Design decisions (settled)

Scoped with the user on 2026-08-07 in the plankit pass, then hardened in a three-round grill the same day. The grill overturned two rows outright — the ignore mechanism and the `logic` artifact — and closed all five original open questions. Where the resolution came from the grill, the row says so.

| Decision | Resolution |
|----------|-----------|
| **Name** | `prototypekit` — per the backlog row. "Prototype" leads so search works, it collides with nothing well-known, and it's the word a user actually types. Rejected `spikekit` (shorter and it *is* the term of art, but "spike" is jargon a non-agile reader misses, and it names only the narrowest of the two branches), `mockkit` (names only the other branch). |
| **Modes** | **Two: `logic` / `ui`.** The split is justified by artifact shape, not topic, and it earns its keep only where a wrong branch wastes the whole prototype — which ui-vs-logic passes and logic-vs-probe does not. **Grilled:** the third `probe` mode for feasibility questions is rejected; instead **`logic`'s recipe branches on who reads the output** — a human clicking gets something interactive, a number or a log gets a script. The gate, the shared rules, the scope box, and the disposal are identical across that branch, so getting it wrong costs a render target rather than the prototype. That closes the "is this library fast enough / do these two interop" case researchkit refuses, without doubling the surface or re-raising "which mode" on every ask. |
| **The question gate** | **No question, no prototype.** Before writing a line, prototypekit states the question and the decision it unblocks, in one sentence each. An ask that resolves to "build me a demo", "make a proof of concept for the client", or "just try something" is **bounced** — that's production work under a softer name, and it belongs to plankit → implementkit. This is prototypekit's version of implementkit's bounce-if-thin, and it's the same success-not-failure framing. |
| **The bounce is not a refusal** | **Grilled.** implementkit never faces this because its bounce names a destination that does the job; prototypekit's destination is two skills away, and a user who repeats the ask has made a decision. So: bounce **once**, naming the reason and the route. If the user reaffirms, **the ask converts, not the skill** — say plainly that this is production work, then do it *as* production work: no `*.prototype.*` marker, no exclude entry, no disposal, kept. The request is legitimate; the *shape* is what was wrong, and honoring it means a demo that survives — precisely what prototypekit's machinery exists to prevent. Never build a demo as a marked, disposed prototype; that hands the user something the skill then deletes. |
| **The stop condition** | **Stop when the question is answered, not when the prototype feels finished.** The failure mode is specific and gradual: a spike that works invites one more case, then error handling, then a component extraction, and the throwaway quietly becomes an app nobody chose to build. **Grilled — the rule now has a mechanism: a scope box.** At the gate, declare the cases **in** and the cases explicitly **out**, and write the box into the prototype file's own header comment beside the stated assumption. Adding a case outside the box requires saying so out loud. The box is in front of the agent every time it reopens the file — which is where drift happens — and it pays twice: the verdict's *what was built* line is written straight from it, which is the rebuild-grade specificity the capture decision depends on. A time box is meaningless to an agent; an artifact ceiling or a case cap is checkable and arbitrary, hitting a dense answer and a sprawling one identically. |
| **Where the code lives** | **In the main working tree, next to what it prototypes, registered in the repo's private exclude.** The reference's rule — locate it close to where it will actually be used, so the imports, aliases, config, and dev server all just work — wins over isolation. Rejected a `gitkit` worktree on a `prototype-<slug>` branch (cleanest disposal in the collection, but real ceremony for a file you intend to delete within the hour) and an out-of-repo scratch dir (maximum safety, and it forfeits the project imports that make a prototype worth building against a real codebase at all). |
| **What a `logic` prototype is made of** | **Grilled — this row overturned the original plan, which contradicted itself.** In-tree placement was justified *by* the project imports, then the recipe mandated one self-contained HTML file that can use none of them; prototype an existing reducer that way and you hand-transcribe it into vanilla JS, so the prototype validates your typing rather than the code. It also silently made this a JS/TS-only skill — a Go state machine has no double-clickable artifact. Resolution: **split on whether the code already exists.** Code that exists runs through the project's own runner and renders however the project can. A model being invented from scratch gets the single self-contained file — still the default there, and still the preferred shape when the project is JS/TS and an import is reachable. The rule, stated flat: **never re-type logic you already have; import it. If you can't import it, the prototype is testing your typing.** |
| **The naming convention is load-bearing** | Every prototype file is named `*.prototype.*`, every prototype directory `*.prototype/`, and **that pattern is what the exclude entry matches**. This is not cosmetic. It's the single mechanism standing between a throwaway and a commit, so the skill states it as a rule with a consequence attached rather than a style note — an unmarked prototype isn't excluded, and an unexcluded prototype is one `git add -A` from main. Both patterns ship, because the file glob won't match a directory on its own. It doubles as the reference's "clearly marked as such": a casual reader sees `cart.prototype.html` and knows. |
| **The exclude entry** | **Grilled — this row overturned the original plan.** The original added `*.prototype.*` to the tracked `.gitignore` on designkit/statuskit's precedent, which broke its own commitkit/reviewkit boundary: a modified tracked `.gitignore` is exactly the uncommitted change both skills *do* see, so the skill would leave a tracked diff behind while reporting it left nothing. It also raised a "which `.gitignore` owns this path" problem in any monorepo. Resolution: **use the repo's private exclude, afkkit's mechanism** — resolve the path with `git rev-parse --git-path info/exclude` rather than hardcoding `.git/info/exclude` (in a linked worktree `.git` is a file), append each pattern only if it isn't already listed, and remove the entry at disposal. Local-only, session-scoped, nothing tracked ever changes. The two precedents cited originally ignore *durable directories* (`docs/status/`, a scratch path) that recur across sessions and teammates; a prototype lives an hour and is deleted by the skill that made it, so the matching precedent is afkkit's. Add the entry **before writing the first file**, and say so in the same line. |
| **What survives** | **No new artifact type.** The answer goes back into whatever asked the question — a plan file, an issue comment, or the chat when neither exists. Rejected `docs/prototypes/prototype-<slug>-YYYY-MM-DD.md` (a ninth `docs/` directory whose contents would be one paragraph). The verdict has a fixed four-line shape wherever it lands — **question · what was built · what it showed · the answer** — so the deliverable is uniform even without a file of its own. |
| **Where the verdict lands in a plan** | **Grilled.** The original wrote the answer into the plan's **Open questions**, which leaves the section misrepresenting the plan's state — an answered question sitting under "open" reads as unhardened, and downstream tooling reads plan state. Resolution: **resolve it** — strike the open question and add the answer to the settled-decisions table, citing the prototype in the row. That's exactly what grillkit does to the same file. This is prototypekit's **one tracked file edit**, it is deliberate, and it only ever touches a file the user named; everything else the skill writes is disposable. |
| **Capture, reconciled** | The reference's rule 6 keeps the prototype as a **primary source** on a throwaway branch. With no worktree and no new artifact, that mechanism returns as an **offer at hand-off, never a default**: "park this on `prototype-<slug>` before I delete it?" — shown as a literal one-line command (`git checkout -b && git add -f && git commit`, then back), not a vague question. **Grilled:** the relitigation worry the reference raises is real, but a branch nobody ever checks out doesn't answer it either, and `prototype-*` branches accumulate with no owner. What answers it is a **rebuild-grade verdict** — *what was built* names the cases driven and the transitions covered, written from the scope box — which survives in the plan, where a decision actually gets reopened. |
| **Disposal is explicit, and confirmed** | prototypekit **deletes the prototype files itself at hand-off** and reports what it removed; a skill that leaves excluded debris behind and calls it disposable is relying on the user to finish the job. **Grilled — the user chose per-file confirmation over auto-delete.** Git cannot recover an excluded file, so the delete is final: the sequence is the **park offer first** as one ask, then **each file listed and confirmed individually**. The exclude entry is removed only when every file is gone; any file the user keeps is reported by absolute path with its exclude line **retained**, which is what keeps the leftover local-only and findable. Anything the skill didn't create in this session, it doesn't touch. |
| **Boundary — researchkit** | researchkit's **Never build to find out** stance is **correct and stays**; only its destination is wrong. Three lines change from "that's implementkit's job" to "that's prototypekit's", and its Open questions template already says *"settling this needs a spike: `<what it would measure>`"* — which becomes a clean hand-off sentence instead of a dead end. The two skills are complements: researchkit answers from sources and never builds, prototypekit answers by building and never cites. |
| **Boundary — implementkit** | **A prototype is never promoted.** Folding a validated decision into the real code is a *fresh* implementkit run against the real files, with its own input, mode resolution, and done-gate — not a copy of the prototype with the marker filed off. Stated in both directions: prototypekit never hands implementkit a file to adopt, and implementkit's bounce-if-thin now has a second destination, since "the design isn't settled because nobody has seen it work" routes here rather than only to grillkit. |
| **Boundary — uikit** | **Borrow the floor, own the divergence.** When uikit is installed, `ui` mode takes its anti-slop catalog and accessibility floor, and **overrides its precedence ladder for this job only** — that ladder's whole purpose is conformity to `DESIGN.md` and the shipped components, and three variants that all conform are variants of one idea, not a choice. Once a variant wins, **uikit builds it for real, from scratch, at full ladder** — the mock is evidence, not a starting point. **Grilled — the uninstalled case is the common one**, since a public skill lands alone in repos with none of the others, and with no floor you get the three-flavors-of-LLM-default failure this plan already names. So `ui` mode carries **its own divergence test, inlined and independent of uikit**: every variant must differ on a **structural axis** — layout, information hierarchy, or interaction model — never on color and spacing, and **each variant names its axis**. The anti-slop catalog is a *polish* floor and stays uikit's; structural divergence is what makes mocks worth comparing, and naming the axis makes plankit's variants-vs-distinct test checkable instead of aspirational. |
| **Boundary — commitkit / reviewkit** | Both are protected by the private exclude, and neither needs to change — and with the exclude replacing the tracked `.gitignore` edit, that is now literally true rather than true-of-the-prototype-files-only. commitkit stages from the working tree and won't see an excluded file; reviewkit targets uncommitted work and won't either. This is the argument that makes in-tree placement survivable, and it's why the naming convention is load-bearing rather than decorative — the guard is the exclude, and the exclude is the name. |
| **Unattended runs** | **Out of `afkkit`'s span, and out of every unattended path.** A prototype exists to produce a judgment a human then makes; running one with nobody watching produces a deleted file and an answer nobody read. Per-file delete confirmation makes this structural rather than advisory. prototypekit is a DECIDE-phase kit like `validatekit` and `researchkit`, which sit outside the span for the same reason. It is interactive-only, in the same class as `mergekit`. |
| **The variant switcher** | The reference's mechanic — one route, a URL search param, a floating bottom bar — ships as the **pattern with its rationale** (a single route means one dev-server start and a shareable link per variant), not as React code. Follow whatever routing the project already uses, and never invent a new top-level structure to hold a mock. **prototypekit never starts a dev server**: shared rule 2 already says one command from the project's own task runner, so the skill names the command and the user runs it. |
| **Variant count** | **Three by default.** Fewer only when three genuinely distinct structural axes can't be named — and then say so explicitly rather than padding the set with a recolor. |
| **When the prototype answers a different question** | **Grilled.** The most valuable outcome of a real spike, and the original plan had no route for it. Resolution: **report and stop.** The verdict states that the asked question is still open, alongside the finding. Following a new question mid-run is the exact drift the scope box exists to catch, wearing a justification, and the user may not want it chased at all. **One carve-out:** when the finding *invalidates the premise* of the asked question — the state model can't exist, so "does it hold up" is moot — that **is** the answer, and it's reported as one. |
| **Visibility** | **Public** (`internal: false`). Conventions inlined, no repo-relative links, no dependency on `make`/`AGENTS.md`/`scripts/`. Degrades to printing the prototype as fenced blocks with their intended paths when there's no writable filesystem — at which point the disposal problem solves itself. |
| **Layout** | **Single flat `skills/prototypekit/SKILL.md`.** Two modes with a recipe each fit one file comfortably — `issuekit` runs five modes in 504 lines. The reference splits into `SKILL.md` + `LOGIC.md` + `UI.md` for progressive disclosure, which is a real benefit in a collection organized that way; here, all 24 skills are single-file and `verifykit`'s helper script is the only second file anywhere. Consistency wins at this size. |

## Approach

**Reuses, rather than reinvents:** `afkkit`'s private-exclude mechanism (`git rev-parse --git-path info/exclude`) for session-scoped, tracking-free scratch; `designkit`'s say-it-in-the-same-line consent phrasing for scratch it writes; `statuskit`'s disposable-by-design framing; `implementkit`'s bounce-if-thin gate, restated for questions instead of specs; `researchkit`'s never-build-to-find-out prose as the mirror image that names this skill's own boundary; `uikit`'s anti-slop catalog and accessibility floor, borrowed under an explicit ladder override and never depended on; `plankit`'s variants-vs-distinct test, given teeth as a named structural axis per variant; `grillkit`'s pattern of resolving an open question into a settled-decisions row; the `Hand off` three-beat closing and the `plan-<slug>-YYYY-MM-DD.md` convention already in force. The reference contributes the two-branch thesis, the six shared rules, and the switcher mechanic.

### Phase 1 — Frontmatter, triggers, and the boundary paragraph

Write `name` / `description` / `license` / `metadata.internal: false` with a front-loaded "Use when…" trigger covering both branches and the plain-English asks — "prototype this", "spike this", "throwaway explore X", "does this state model hold up", "is this library fast enough", "show me a few options for this screen", "mock up three versions". The opening names what prototypekit is **not**: not implementkit (production code, gated), not researchkit (answers from sources, never builds), not uikit (builds the UI that ships), and not a demo generator. Three of those are sibling skills; the fourth is the shape the request most often arrives disguised as.

### Phase 2 — The question gate, the scope box, and branch routing

The step before any code, in three beats.

**State the question** and **the decision it unblocks**, one sentence each. **Bounce** anything that resolves to "build me a demo" back to plankit → implementkit with the specific reason named — once. If the user reaffirms, say plainly that this is production work and then do it as production work: unmarked, unexcluded, undisposed, kept, and prototypekit stops driving.

**Declare the scope box** — the cases in, the cases explicitly out — and carry it into the prototype file's header comment. Nothing outside the box gets built without saying so first.

**Route the branch:** a state model, a reducer, a flow, a backend module, a feasibility question → `logic`; a page, a screen, a component → `ui`. Where the ask is genuinely ambiguous and the user isn't reachable, default by what surrounds the code and **state the assumption at the top of the prototype**, next to the scope box — a stated wrong assumption is correctable and a silent one isn't.

### Phase 3 — The shared rules

The six that apply to both branches, adapted to this collection's mechanisms rather than restated:

1. **Throwaway from day one, and marked.** Next to what it prototypes; `*.prototype.*` for files and `*.prototype/` for directories; the private-exclude entry added first, via `git rev-parse --git-path info/exclude`, and named in the same line.
2. **Trivial to run.** One command from the project's own task runner, or a file you double-click. Discover the runner from the repo (`package.json`, `Makefile`, `justfile`, `pyproject.toml`, `go.mod`, `Cargo.toml`) rather than assuming one — and **name the command; never start a server yourself.**
3. **No persistence.** State lives in memory. Persistence is usually the thing being checked, not something to depend on; when the question genuinely involves a database, a scratch DB named `PROTOTYPE_wipe_me`.
4. **Skip the polish.** No tests, no abstractions, no error handling past what makes it run. prototypekit **never runs a done-gate** — there is nothing to gate.
5. **Surface the state.** Every action (logic) or variant switch (ui) renders the full relevant state. An invisible prototype answers nothing.
6. **Stop when it's answered.** The scope box is the check: a case outside it is a new decision, announced, not absorbed.

### Phase 4 — Mode: `logic`

**Two shapes, chosen by whether the code already exists** — and the rule that picks between them is the one stated in the decisions table: never re-type logic you already have.

**Code that exists** runs through the project's own runner, importing the real module, and renders however the project can — a throwaway dev route, a CLI harness, a script. This is the case in-tree placement was chosen for, and it's the only shape that tests the actual code rather than a transcription of it. It is also the shape that makes the skill work outside JS/TS at all.

**A model being invented from scratch** gets **one self-contained file** — for a web project, HTML with no build step and no server, double-click to open, shareable as a single attachment to someone who doesn't have the repo; for anything else, that language's simplest runnable single file.

Then the second axis, **who reads the output**. A **human clicking** gets the interactive shape: **free-play controls** that fire every transition, plus **tabbed guided walkthroughs** that push the model through the specific cases the question is about, with full state rendered after every action. A non-developer must be able to drive it, because "does this feel right" is frequently a question only a non-developer can answer. A **number or a log** — is this fast enough, do these two interop, does this API do what its docs imply — gets a script that prints the measurement and the conditions it was taken under. Same gate, same scope box, same disposal; only the render target differs.

### Phase 5 — Mode: `ui`

**Three structurally different variations on a single route**, switchable via a URL search param and a floating bottom bar, so one dev-server start covers all of them and each variant has a shareable link.

Divergence is the deliverable, and the test is inlined here rather than borrowed: **each variant must differ on a structural axis — layout, information hierarchy, or interaction model — and must name the axis it takes.** Differing on color and spacing is a recolor, not a variant, and three variants of one idea is a failed prototype. Fewer than three ships only when three distinct axes genuinely can't be named, and then the skill says so instead of padding.

When uikit is installed, borrow its anti-slop catalog and accessibility floor, and **override its precedence ladder for this job only, out loud**. When it isn't — the common case for a public skill — the structural divergence test stands alone and is enough. Naming and routing follow whatever the project already does; never invent a new top-level structure to hold a mock.

### Phase 6 — The verdict, capture, and disposal

The closing sequence, in order:

**Verdict** — question · what was built · what it showed · the answer, with *what was built* written from the scope box so it names the cases driven and transitions covered, specific enough to rebuild from. It lands in whatever asked the question: in a plan file, **strike the open question and add a settled-decisions row citing the prototype** — the skill's one tracked edit, always to a file the user named; otherwise an issue comment, otherwise the chat. When the prototype answered a *different* question, the verdict says the asked one is still open and reports the finding beside it — unless the finding invalidated the question's premise, which is itself the answer.

**Offer the park** — `prototype-<slug>`, off by default, shown as the literal command.

**Delete, confirmed per file** — list each file created this session and confirm each individually, because git cannot recover an excluded file. Remove the exclude entry only when every file is gone; report any kept file by absolute path and leave its exclude line in place.

Then `## Hand off`, three beats: what changed (files created, which were deleted and which the user kept, the exclude entry's fate, whether the branch park happened), where the answer landed, and one next move — normally `plankit`/`grillkit` to fold the answer into the plan, `uikit` when a variant won and needs building for real, and `domainkit` when the answer settled a hard-to-reverse trade-off worth an ADR. Each named only when installed, each with a plain-language fallback.

### Phase 7 — Integration

- **`researchkit`** — three lines redirected from implementkit to prototypekit (the **Never build to find out** close, the primary-sources spike aside, and the Open questions template note). Its stance is unchanged; only the destination moves. The feasibility cases at `researchkit:48` now have a real home in `logic`'s script shape.
- **`implementkit`** — one line in its bounce step: an input thin because *nobody has seen the design work* routes to prototypekit, alongside the existing grillkit/plankit routes.
- **`commitkit` / `reviewkit`** — **no change**, and now genuinely so: the private exclude leaves no tracked diff for either to see.
- **`WORKFLOW.md`** — prototypekit added to the DECIDE phase next to `validatekit` and `researchkit`, in both the ASCII map and the Mermaid diagram, with a short section covering both modes and the never-unattended note.
- **`README.md`** skills table, **`skills.sh.json`** (the **Planning & Design** group), and the `prototypekit` row **deleted from `IDEAS.md`** per its own graduation rule.

### Phase 8 — Test live

`make link`, then run all three shapes against a real project — an existing reducer for `logic`'s import path, an invented model for its single-file path, a feasibility script for its measurement path, and a real screen for `ui`. Confirm specifically: the exclude entry lands via `rev-parse` and not a hardcoded path, `git status` stays clean throughout, per-file delete confirmation fires, a kept file retains its exclude line, and nothing survives that shouldn't. Then `make lint`.

## Open questions

**None open.** The five that stood here were settled in the 2026-08-07 grill and moved into the decisions table: feasibility probes fold into `logic` via the reader branch; the branch park stays an offer, backed by a rebuild-grade verdict; the tracked `.gitignore` edit is replaced by afkkit's private exclude; the stop condition gains a scope box; and a prototype that answers a different question reports and stops. Two decisions the grill added — the reaffirmed-demo path and `ui`'s uikit-free divergence test — are recorded there too.

One risk to watch in **Phase 8** rather than settle on paper: `logic`'s three shapes are described in prose but only proven by running them. If the import path turns out to need per-language scaffolding advice to be usable, that's a drafting expansion, not a reopened decision.

## Non-goals

- **Not production code.** No tests, no error handling, no abstractions, no done-gate — and never promoted. Folding a validated decision into the real code is a fresh `implementkit` run.
- **Not a demo generator.** A prototype answers a question. Something built to show a client or a stakeholder bounces once; if reaffirmed it gets built as production work, unmarked and undisposed — never as a throwaway the skill then deletes.
- **Not the research step.** `researchkit` answers from primary sources and never builds. prototypekit answers by building and cites nothing.
- **Not the UI builder.** `uikit` builds the UI that ships. prototypekit's mocks exist to be compared, chosen between, and deleted.
- **Not a design-system artifact.** It reads `DESIGN.md` only through uikit's floor and never writes it — that's `designkit`'s, exclusively.
- **Never unattended.** Out of `afkkit`'s span and every autonomous path; the deliverable is a human judgment, and per-file delete confirmation makes that structural.
- **Does not commit** (except the explicitly offered branch park), does not push, does not open a PR, does not file an issue, does not start a dev server.
- **Touches no tracked file** except the one plan or issue the user named as the verdict's destination — the private exclude is local-only by design.
- **Not a scratch-file manager.** It disposes of what it created in this session and nothing else.
